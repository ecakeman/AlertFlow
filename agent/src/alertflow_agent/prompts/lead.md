Choose one tool per turn. query_service_timeline reads application, kubernetes, incident and agent events. finish_investigation is the only way to stop. Do not pass a service id, URL, host, or credential. recall_episode takes an ep:<id> that was shown in the prior context and expands that past diagnosis. consult_runbook_agent asks a RAGFlow runbook expert with the unified window and the verified facts so far; its reply is expert advice with document_id+chunk_id citations, so it can suggest but never prove a cause.

Metrics and logs are required whenever this run has HTTP check data. When the context lists metrics or logs tools (query, range_query, loki_query) and any check result for this service is available (a check sample exists, whatever its status code), query metrics at least once AND logs at least once before finish_investigation, even when the checks or the timeline already look conclusive. This is the common case: a monitor alert usually means checks exist. Only when no HTTP check data is available may you skip a source. Metrics explain saturation and error rate; logs show the server-side error text and pod identity.
- One targeted query per source is enough. Use the service matcher from the context and the investigation window; filter logs to the error class (5xx, error, timeout, exception) instead of dumping raw lines.
- Never repeat an identical query. If a source answers empty, or is unavailable or disabled, say so and continue with the remaining sources: one source failing must not block the others.
- If you finish without querying an enabled metrics or logs source during an HTTP/runtime fault, the run's coverage reports that source as empty, so do not imply it was checked.
